- 9 warnings remain, all real, all matching the issue's remaining scope:
  - `client/src/hooks/useAddWorkoutByUserId.ts:40` — `no-unsafe-argument`
  - `client/src/hooks/useDeleteWorkoutById.ts:36` — `no-unsafe-argument`

Goal: 0 warnings on `yarn lint` (client + serverless), no behavior change.

## Approach

### 1. Client mutation hooks — reuse `IResponseWithError`

`client/src/hooks/useAddWorkoutByUserId.ts:31-43` and
`client/src/hooks/useDeleteWorkoutById.ts:25-39` both do:

```ts
const _response = await authedFetch.post(/* ... */) // Promise<any>
if (_response?.error) { throw new Error(_response.error) }
return _response
```

`authedFetch.post`/`.delete` are typed `Promise<any>` in `react-netlify-identity`'s
declarations, so `_response.error` is an unsafe argument. `client/src/hooks/helpers/types.ts`
already exports `IResponseWithError` (`{ error?: string }`) for exactly this pattern — apply
the same `as T & IResponseWithError` cast used in `useGetWorkoutById.ts:44` /
`useListByUserId.ts`. No behavior change, only a type annotation.

### 2. `serverless/pompom.d.ts:14,19` — narrow `Record<string, any>`

Both `identity?: Record<string, any>` occurrences (in `Context` and `LambdaContext`) hold an
unstructured payload from the auth provider — nothing in the codebase indexes into known keys.
Change to `Record<string, unknown>`, which keeps the "arbitrary bag of values" shape but
removes the `any` warning. Verified via `grep -rn "\.identity\b"` across `serverless/` that no
call site accesses a specific key expecting `any`'s implicit-conversion behavior.

### 3. `serverless/setup-server-tests.ts:30,31` — typed empty stubs

`env: {} as any` / `client: {} as any` are stub values for `ClientContextEnv` /
`ClientContextClient` (from `@types/aws-lambda`), which have required string fields the mocks
don't fill in (there's already a `// TODO: change this to remove the any` comment here). Change
the casts to `{} as ClientContextEnv` / `{} as ClientContextClient` — same incomplete-stub
behavior, but a typed cast instead of `any`, matching the existing TODO's intent. Requires
importing `ClientContextEnv`, `ClientContextClient` from `aws-lambda`.

### 4. `add-workout-by-user.test.ts:204` — type the `JSON.parse` result

`const workout = JSON.parse(body as Stringified<Workouts>)` returns `any`, making
`workout.id` (line 204) and `workout[key]` (used later) unsafe. `body` is already asserted as
`Stringified<Workouts>`, so the parse result should be typed `Workouts`:
`JSON.parse(body as Stringified<Workouts>) as Workouts`.

### 5. `delete-workout-by-id.test.ts:103` — type the invalid-event fixture

`{} as any` at line 103 deliberately passes a malformed event to test the validator's error
path (the following lines assert a 500 + specific error message). Replace with
`{} as HandlerEvent<unknown, unknown>` — matches the handler's actual parameter type
(`HandlerEvent<T, Q>` from `serverless/pompom.d.ts`) while keeping the object empty/invalid at
runtime, so the test still exercises the same validation-failure path.

### What shipped on branch 1

Two of the five planned fixes didn't compile as written and needed a different approach:

- **`serverless/pompom.d.ts` `identity` field**: the plan proposed `Record<string, unknown>`.
  This broke `tsc` — the real AWS `CognitoIdentity` type has no index signature, so it isn't
  structurally assignable to any `Record<string, ...>` narrower than `any`. Used
  `NtlHandlerContext['identity']` instead (resolves to `CognitoIdentity | undefined`), which
  is both correctly typed and removes the `any` warning.
- **`delete-workout-by-id.test.ts` malformed-event fixture**: the plan proposed
  `{} as HandlerEvent<unknown, unknown>`. This didn't match the middy-wrapped handler's actual
  inferred parameter type and produced new `tsc` errors. Code review then found the sibling
  file `add-workout-by-user.test.ts` already had a disable-free pattern for the exact same
  "malformed event" case: `createMockHandlerEventBody<T, null>({} as T, null)`. Switched to
  that pattern — both `createMockHandlerEventBody` and `DeleteWorkoutByIdMutationVariables`
  were already imported in the file, so this needed no new eslint-disable comments.
- **`add-workout-by-user.test.ts:206`** keeps one eslint-disable
  (`@typescript-eslint/no-unsafe-argument`) on `workoutsIdToCleanUp.push(workout.id)`. Root
  cause: `Workouts['id']` is a GraphQL `uuid` scalar, and codegen maps `uuid` to `{ input: any;
  output: any }` — so `workout.id` is `any` even though `workout` itself is correctly typed as
  `Workouts`. Fixing this at the source means adding a custom scalar mapping in the
  `graphql-codegen` config, which is out of scope for a lint-cleanup change. Verified this is
  the only remaining disable comment in the diff (`delete-workout-by-id.test.ts` no longer
  needs one after the fix above).

Final result: `yarn lint` 0 warnings/0 errors (client + serverless), `yarn test` 31/31,

`createMockHandlerEventBody` reuse fix was applied.
