## Context

Sub-issue B of #88 (https://github.com/nathpaiva/pompom-time/issues/88). Branches from
`main` at `51d3947` (#102 merged: static layout, real data, no animation).

#102 gave `WorkoutTime.tsx` a real layout but left `usePulse` untouched — it still runs on
raw `setInterval` ticks with 4 boolean flags (`isPulsing`/`isResting`/`isCountingDown` +
counters). This issue replaces that with an explicit phase state machine and the
per-variety timing table from the design spec, still with **no smooth animation** — phase
changes are discrete snaps. Continuous motion (rAF, SVG ring, RGB lerp) is #104.

## Current `usePulse` behavior (baseline, must not silently change)

Read `usePulse.ts` in full before touching it — this is the file every downstream screen
depends on. Key existing behavior to preserve or deliberately supersede:

- `handleStartStopPulse()` toggles pulsing; while pulsing, calling it again stops and
  resets to 0 (acts as "Reset" during an active set).
- Countdown is 3→2→1 at 1s/tick, `PULSE_INTERVAL_RESTING = 1000`.
- Pulse tick interval come from `intervalByWorkoutType` (Pulse/Intensity/Resistance = 500ms,
  Strength = 1500ms) unless `variety === Resistance` and `interval` is set, then
  `interval * 1000`.
- `advanceSet` decides whether to go to rest or finish the workout — has the known bug
  (documented in #102's PR #105, deferred here) where `counter` resets to 0 after the final
  set with no distinct "done" signal, and never resets at all if `repeat` is falsy.
- `PULSE_LIMIT = 20`, `PULSE_INTERVAL_FALLBACK = 500` — check both are still needed after
  the rewrite; `PULSE_LIMIT` looks unused already (grep before removing).

## New state machine (from the #88/#103 issue spec)

```
idle -> countdown (3,2,1 @ 1s/tick)
  -> contract (ease-out scale 1 -> minScale over "contract" ms)
    -> [Resistance only] hold (flat at minScale for "interval" seconds, ring sweeps in #104)
  -> release (ease-in-out scale back to 1 over "release" ms)
  -> loops contract->release until reps == squeeze count
  -> resting (counts down "rest" seconds) -> countdown again -> next set
  -> after final set -> done
```

`done` is a **new** phase this issue adds — #102's deferred bug (header shows "Set 1 of N"
again after the last set) gets fixed here by giving the UI a real terminal phase to read
instead of inferring completion from `counter` resetting to 0.

## Per-variety timing table

| Variety | contract | release | hold | minScale |
|---|---|---|---|---|
| Pulse | 280ms | 280ms | none | 0.62 (fixed) |
| Intensity | 480ms | 380ms | none | `max(0.42, 0.7 - 0.045 * repIndex)` |
| Resistance | 600ms | 400ms | `interval` seconds (from workout data) | 0.6 (fixed) |
| Strength | 500ms | 500ms | none | 0.58 (fixed), + `translateY` up to -40px (value only) |

Easing: contract = ease-out `1 - (1-t)^2`, release = ease-in-out. Both computed in
`phaseMath.ts` (below); this issue only needs the value at **100% progress** of each phase
(the snap target) since there's no continuous rendering yet.

## Approach

### 1. `phaseMath.ts` — pure, no timers, no React

New file `client/src/pages/WorkoutTime/hooks/usePulse/phaseMath.ts`:

```ts
computePhaseState(phase: TPhase, elapsedMs: number, variety: Variety_Enum, repIndex: number)
  -> { scale: number, color: string, translateY: number, ringOffset: number }
```

- Looks up the timing table entry for `variety`, applies the right easing for
  `contract`/`release`, clamps `elapsedMs / durationMs` to `[0, 1]`.
- `color`: RGB-interpolated from `#F2C6B6` (relaxed) toward the variety's color
  (`varietyColorMap`), by contraction progress — #104 will actually render this
  continuously; this issue only needs the function to exist and be correct, tested with
  direct input values at 0%, 50%, 100% of each phase.
- `translateY`: 0 for all varieties except Strength, where it scales with contraction
  depth, floor at -40px.
- `ringOffset`: only meaningful during Resistance `hold`; 628.3 → 0 as hold progresses.
  Compute it here even though #104 is what actually draws the SVG ring — keeps all
  phase-derived math in one pure, testable place.
- Fully unit-tested in `phaseMath.test.ts`: one test per variety, asserting exact values at
  0%, 50%, 100% of `contract`, and (for Resistance) `hold`/`release`.

### 2. `usePulse.ts` rewrite

- Replace the 3 separate boolean-flag state groups with one `phase: TPhase` state
  (`'idle' | 'countdown' | 'contract' | 'hold' | 'release' | 'resting' | 'done'`), plus
  `repIndex`, `setIndex`.
- **`countdown` and `resting`**: keep the existing `setInterval`-1s-per-tick model
  (`PULSE_INTERVAL_RESTING`), unchanged in mechanism — only the phase they set on
  completion changes (`countdown` → `contract`, `resting` → `countdown` or `done`).
- **`contract` / `hold` / `release`**: replace the fixed-tick `setInterval` with a single
  `setTimeout` sized to that phase's duration from the timing table (for `hold`, the
  workout's own `interval` in seconds). On timeout, advance to the next phase.
- **Pause** (mid-`contract`/`hold`/`release`): capture `Date.now() - phaseStartedAt` into a
  `pausedElapsedMs` ref, clear the pending `setTimeout`. On resume, reschedule for
  `remainingMs = phaseDurationMs - pausedElapsedMs`, reset `phaseStartedAt` to now. Add a
  test asserting elapsed time survives a pause/resume cycle (pause mid-contract, resume,
  confirm the phase still completes at the original total duration, not restarted).
- **Reps loop**: `contract → [hold] → release` repeats until `repIndex === squeeze`, then
  `resting` (more sets left) or `done` (final set) — this is what fixes #102's deferred
  "Set 1 of N again" bug, since `done` is now a distinct, terminal phase the UI can check.
- Public return shape changes — this is a **breaking change** to `usePulse`'s consumers.
  `WorkoutTime.tsx` (#102's phase-derivation ternaries) needs updating in the same PR
  (folding in #106's refactor — see below).

### 3. Fold in #106 (phase derivation refactor)

#102's code review flagged `WorkoutTime.tsx`'s inline `phase`/`phaseLabel`/`statusText`
derivation as something to extract once the phase set grows (issue #106). This rewrite
*is* that growth — the old 4-phase inline ternary chain in `WorkoutTime.tsx` doesn't scale
to 7 phases + rep-relative color/scale. Move the phase-to-display mapping into a small
helper (e.g. `useWorkoutPhaseDisplay(usePulseResult, workout)` in a sibling file to
`usePulse`, or a plain function) so `WorkoutTime.tsx` stays a thin composition layer.
Closes #106 as part of this PR rather than deferring further.

### 4. `WorkoutTime.tsx` + components — no visual change expected

Since #104 (not this issue) adds the actual smooth motion and SVG ring, `WorkoutTime.tsx`
should render the **same static appearance** as after #102, just reading from the new
`phase` enum instead of the 3 old booleans. `BreathingCircle`, `RepDots`,
`VarietySwitcher`, `WorkoutControls` (from #102) should not need prop-shape changes — the
new `useWorkoutPhaseDisplay` helper maps the new phase set back onto the same
`phaseLabel`/`statusText`/`completedReps`/button-disabled props those components already
accept. Re-run #102's Playwright screenshot check to confirm zero visual regression.

## What shipped on branch 1

Followed the plan's approach (phaseMath.ts pure function, usePulse rewritten around an
explicit `phase` state, #106's `useWorkoutPhaseDisplay` extracted in the same PR). Two
implementation details diverged from the plan as written:

- **Root cause found during implementation, not review**: the first `usePulse` draft used
  `useCallback` for the mutually-recursive phase functions (`enterPhase` calling
  `advancePhase` and vice versa). This produced a stale-closure bug — `enterPhase`'s
  `setTimeout` always called the *first* version of `advancePhase` ever created (with
  `repIndex` frozen at 0), because `advancePhase` couldn't be in `enterPhase`'s deps without
  a circular dependency. Root-caused via `superpowers:systematic-debugging`; fixed by moving
  the phase functions into refs, reassigned inside a single `useEffect` after every render
  (not `useCallback`), so timer callbacks always call the current version.
- **`react-hooks/refs` eslint rule**: the ref-reassignment fix above initially wrote to
  `.current` directly in the hook's render body, which the newer `eslint-plugin-react-hooks`
  rejects ("Cannot access refs during render"). Fixed by moving all ref assignment inside the
  `useEffect` body (which already existed for the stale-closure fix) instead of the render
  body directly — same fix covers both problems.

Code review (`code-review` skill, effort `high`, 4 parallel angles) on the first working
draft found 7 issues, with the same top finding confirmed independently by all 4 review
agents:

- **Fixed**: Reset button was wired to the exact same handler as the primary Start/Pause
  button (`pulse.handleStartStopPulse`), so it silently paused instead of resetting during
  `contract`/`hold`/`release`. Gave `usePulse` a separate `handleReset` (always calls
  `reset()`, phase-independent) and wired `WorkoutControls`'s `onResetClick` to it instead.
- **Fixed**: tapping the primary button during `countdown` or `resting` discarded all
  progress (fell through to `reset()`) instead of pausing — the old code path only had a
  real pause/resume model for `contract`/`hold`/`release`. Unified `countdown` and `resting`
  onto the same `setTimeout`-based `enterPhase`/`advancePhase` mechanism as the other phases
  (one 1-second tick at a time via new `tickCountdownRef`/`tickRestingRef`), so `pause()`/
  `resume()` now work identically across every active phase — the primary button never
  discards progress, only `handleReset` does.
- **Fixed** (cleanup): `usePulse.ts` declared its own local `TPhase` type instead of
  importing it from `phaseMath.ts` (which `types.ts` already did) — two independent
  declarations of the same union. Now `usePulse.ts` imports `TPhase` from `phaseMath.ts`.
- **Fixed** (cleanup): contract/release timing lived in two places — `constants.ts`'s
  `contractMsByVariety` and `phaseMath.ts`'s private `CONTRACT_MS`/`RELEASE_MS`. Removed
  `contractMsByVariety` entirely; `phaseMath.ts` now exports `phaseDurationMs(phase, variety,
  holdSeconds)` as the single source both `usePulse.ts` (real timers) and
  `computePhaseState` (animation math, still unwired — see below) read from.
- **Fixed** (cleanup): the `useEffect` reassigning the phase-function refs had no dependency
  array (reran and reallocated 4 closures on every render, including every 1-second tick).
  Added the real dependency list (`variety`, `holdSeconds`, `squeeze`, `sets`, `repeat`,
  `rest`, plus the ref-setter callbacks).
- **Fixed** (cleanup): no cleanup cleared the pending timer on unmount — navigating away
  mid-phase (e.g. clicking Back) left a dangling `setTimeout` that would fire against a
  stale closure after unmount. Added a `useEffect` returning `() => clearPendingTimer()`.
- **Confirmed expected, not a bug**: `phaseMath.ts`'s `computePhaseState` (RGB color lerp,
  scale, `translateY`, ring sweep) is fully implemented and unit-tested but has zero
  consumers in the render path — `BreathingCircle` still renders a static box. This is
  correct for this issue's scope (per the plan: "#104 will actually render this
  continuously; this issue only needs it to compute the value at 100% of each phase, the
  snap target"). Flagged by all 4 review angles independently since it reads as dead code in
  isolation — worth keeping in mind when #104 starts, since the wiring is the whole point of
  that issue.
